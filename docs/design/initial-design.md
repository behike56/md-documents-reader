# `md-documents-reader` 初期設計

## 文書の位置づけ

この文書は、`md-documents-reader` の実装を開始するための設計ドラフトである。主な読者は、設計をレビューする開発者と、今後の実装担当者を想定する。

現時点では、Rust のバイナリクレートと静的チェック環境だけが実装されている。Markdown 文書を読み取る機能や利用者向けインターフェースは未実装であり、本書の機能設計は「提案」として扱う。

## 確認済みの現状

リポジトリから確認できる事実は、次のとおりである。

| 項目 | 現状 | 情報の正 |
| --- | --- | --- |
| 実装言語 | Rust 2024 Edition | `md-documents-reader/Cargo.toml` |
| 成果物 | バイナリクレート | `md-documents-reader/src/main.rs` |
| 外部依存 | なし | `md-documents-reader/Cargo.toml` |
| 実装済みの動作 | 標準出力への `Hello, world!` 表示 | `md-documents-reader/src/main.rs` |
| 品質チェック | `rustfmt`、Clippy、`cargo check` | `Makefile`、`.github/workflows/static-checks.yml` |

## 目的

初期実装では、次の処理を小さな責務に分け、Markdown 文書の取得方法や表示方法を後から変更できる構造を目指す。

1. 読み取り対象を受け取る。
2. 対象から Markdown のテキストを取得する。
3. テキストを文書として解釈する。
4. 利用者が読める形式で提示する。
5. 失敗理由を利用者に伝える。

この処理順は設計の骨格を示すものであり、具体的な入力方式、Markdown の解釈範囲、表示形式は未確定である。

## 対象範囲

### 初期設計に含めるもの

- 単一の Markdown 文書を扱う基本フロー
- 入力、文書処理、出力の責務分離
- ファイルや構文のエラーを呼び出し元へ返す方針
- コアロジックを入出力から分離してテストする方針
- 将来の入力方式・表示方式の追加に備えた境界

### 初期設計に含めないもの

次の項目は要求が確認できていないため、初期設計では仕様を確定しない。

- GUI、TUI、Web UI の採用
- 複数文書のライブラリ管理、全文検索、タグ付け
- Markdown の編集、保存、同期
- 外部 URL からの取得
- 独自 Markdown 拡張
- HTML の安全化ルール
- 大容量ファイルに対する具体的な性能目標

## 設計方針

### 責務を3つの領域に分ける

処理を「インターフェース」「アプリケーション」「文書処理」の3領域に分ける。

```text
[利用者]
   |
   v
[インターフェース]
  入力の受付 / 結果の表示 / 終了状態への変換
   |
   v
[アプリケーション]
  ユースケースの進行 / 入力元と出力先の調停
   |
   v
[文書処理]
  Markdown 文書の表現 / 解釈結果 / 文書固有の検証
   |
   +----> [入力アダプター: ファイルなど]
   |
   +----> [出力アダプター: プレーンテキストなど]
```

この分割により、ファイル読み取りや画面表示の詳細が、Markdown 文書を扱うコアロジックへ混入することを避ける。

### 初期段階では単純な構造を保つ

最初から抽象化を増やしすぎず、異なる実装へ差し替える必要が確認できた境界だけを分離する。特に、入力元と出力先が1種類しかない間は、トレイトの導入を必須としない。

ただし、次の依存方向は維持する。

```text
インターフェース -> アプリケーション -> 文書処理
                         |
                         v
                    入出力の境界
```

文書処理は、CLI 引数、終了コード、端末制御、ファイルシステム API に依存しない。

## 提案する処理フロー

初期のユースケースを「指定された1つの Markdown 文書を読み、提示する」と仮定する。

```text
1. インターフェースが読み取り対象を受け取る
2. アプリケーションが入力アダプターへテキスト取得を依頼する
3. 入力アダプターが Markdown テキストを返す
4. 文書処理がテキストを解釈し、提示用の表現を返す
5. アプリケーションが出力アダプターへ結果を渡す
6. インターフェースが成功または失敗を利用者へ通知する
```

入力方式と出力方式が確定していないため、上記は特定の UI やライブラリを前提としない。

## 提案するモジュール構成

機能追加時は、まず次の最小構成を候補とする。実装前の提案であり、現時点では `main.rs` 以外は存在しない。

```text
md-documents-reader/src/
  main.rs             # プロセスの起動と依存関係の組み立て
  app.rs              # 文書を読み取るユースケース
  document.rs         # 文書の表現と文書固有の処理
  input/
    mod.rs            # 入力境界
    file.rs           # ローカルファイルからの取得
  output/
    mod.rs            # 出力境界
    text.rs           # 初期の提示方式
  error.rs            # アプリケーション境界のエラー分類
```

ファイル分割は責務や変更理由が実際に分かれた時点で行う。小規模な間は、同じ責務を保ったまま少ないファイルで実装してもよい。

## データと境界

### 入力

アプリケーションが必要とする入力は、「読み取り対象を識別する値」である。初期候補はローカルファイルのパスだが、正式な入力方式は要確認とする。

入力アダプターは、対象から UTF-8 テキストを取得し、取得失敗をアプリケーションで扱えるエラーへ変換する責務を持つ。パスの表示方法や OS エラーの詳細をどこまで利用者へ見せるかは、インターフェース側で判断する。

### 文書

文書処理は、少なくとも元の Markdown テキストを受け取る。見出し、段落、リンク、コードブロックなどを構造化する必要があるかは、表示要件が確定してから決める。

Markdown パーサーを採用する場合、パーサー固有の型をアプリケーション全体へ露出させず、必要な表現へ変換する。これにより、ライブラリの変更が入出力やユースケースへ波及する範囲を限定する。

### 出力

出力は「利用者が文書を読める表現」を受け取る。プレーンテキスト、ANSI 付きテキスト、HTML、画面ウィジェットのどれを採用するかは要確認である。

文書処理は、端末への書き込みや UI の更新を直接行わない。これらの副作用は出力アダプターに閉じ込める。

## エラー設計

初期実装では、利用者が次の行動を判断できる粒度でエラーを分類する。

| 分類 | 例 | 利用者が取れる行動 |
| --- | --- | --- |
| 入力不正 | 対象が指定されていない、対応しない入力形式 | 入力を修正する |
| 取得失敗 | ファイルが存在しない、権限がない、読み取りに失敗した | 対象や権限を確認する |
| デコード失敗 | UTF-8 テキストとして解釈できない | 文字コードまたはファイルを確認する |
| 文書処理失敗 | 対応する構文として処理できない | 文書または対応範囲を確認する |
| 出力失敗 | 標準出力や表示先への書き込みに失敗した | 表示先の状態を確認する |

下位層のエラーを文字列だけに変換せず、分類と原因を保持する。利用者向けメッセージと、開発者が原因を追跡する情報は分けて扱う。

## 品質方針

### 正しさ

- 入力テキストを暗黙に変更しない。
- 構文を解釈する場合は、採用する Markdown 仕様と拡張を明示する。
- エラー時に成功として扱わず、呼び出し元へ失敗を返す。

### セキュリティ

- 入力文書を信頼済みと仮定しない。
- HTML を生成または表示する場合は、生 HTML、スクリプト、危険な URL スキームの扱いを実装前に決定する。
- 外部リンクや画像を自動取得する場合は、ネットワークアクセスの可否と制限を別途設計する。

### 性能

- 初期実装は単一文書の全体読み込みを候補とする。
- 許容ファイルサイズと応答時間の目標は、利用環境が確定した後に決める。
- 大容量文書や複数文書の処理が必要になった場合に限り、ストリーミングやキャッシュを検討する。

### 保守性

- 純粋な文書処理と I/O を分離する。
- 外部ライブラリ固有の型を境界の内側に閉じ込める。
- 依存を追加するときは、必要な機能、更新状況、ライセンス、代替可能性を確認する。

## 検証方針

実装時は、責務ごとに次を確認する。

| 対象 | 主な検証 |
| --- | --- |
| 文書処理 | 空文書、通常の Markdown、Unicode、コードブロック、リンクなどの単体テスト |
| 入力アダプター | 正常なファイル、存在しないファイル、権限、非 UTF-8 入力のテスト |
| アプリケーション | テスト用の入出力を使った処理順序とエラー伝播のテスト |
| インターフェース | 引数や操作の受け付け、利用者向けメッセージ、終了状態の結合テスト |
| 静的品質 | `rustfmt`、Clippy、`cargo check` |

Markdown の具体的な期待結果は、採用する仕様と表示方式が決まってからテストケースとして固定する。

## 設計判断とトレードオフ

| 判断 | ステータス | 利点 | コスト・制約 |
| --- | --- | --- | --- |
| 入力・アプリケーション・文書処理・出力を分離する | 提案 | I/O とコアロジックを独立して変更・テストできる | 初期コード量が増える可能性がある |
| 差し替えが必要になるまで抽象化を最小限にする | 提案 | 小規模な実装で不要な複雑性を避けられる | 後から境界を抽出する変更が発生し得る |
| 単一文書の処理から始める | 提案 | 最小のユースケースで設計を検証できる | 文書間リンクや検索の要求は別途設計が必要になる |
| 文書全体をメモリへ読み込む | 要確認 | 実装が単純で、一般的なパーサーを利用しやすい | 大容量文書には適さない |
| 初期入力をローカルファイルとする | 要確認 | オフラインで扱え、責務が明確になる | 標準入力や URL が主要用途なら設計を見直す必要がある |
| 初期出力をプレーンテキストとする | 要確認 | UI 技術への依存を抑えられる | Markdown の視覚表現が限定される |

## 実装の進め方

設計を確定した後は、次の順序で小さく実装・検証する。

1. 主要な利用方法と入出力方式を決める。
2. 単一文書の読み取りに対する観測可能な振る舞いを決める。
3. 文書処理を I/O から独立した関数として実装する。
4. ローカル入力など、決定した入力アダプターを実装する。
5. 決定した出力アダプターとインターフェースを接続する。
6. 正常系、境界値、失敗系をテストする。
7. 静的チェックと実行確認を行う。

## 要確認事項

実装へ進む前に、少なくとも次を決定する必要がある。

1. 主な利用者と利用場面は何か。
2. CLI、TUI、GUI、Web のどれを主要インターフェースとするか。
3. 入力はローカルファイル、標準入力、ディレクトリ、URL のどれを対象とするか。
4. Markdown をどのように提示するか。構文を保持したテキスト表示か、装飾表示か、HTML 変換か。
5. CommonMark、GitHub Flavored Markdown など、どの仕様と拡張を対象とするか。
6. 生 HTML、画像、外部リンクを許可するか。
7. 1文書あたりの想定サイズと、必要な応答性能はどの程度か。
8. 読み取り専用のツールか、将来は編集・管理まで対象にするか。
